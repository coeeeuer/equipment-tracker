# Central Hospital rollout notes

## Scope delivered in this branch

- Adds a hospital location directory for wards and departments.
- Adds a canonical asset register with database-side search, status/department/category filters and server-side pagination (25/50/100 rows). Central admin/Biomedical users can register and edit assets; asset codes are generated by the database trigger. Central users can transfer an asset through an atomic database function that updates its current department/location and records transfer history.
- Seeds the eight initial locations agreed for Central Hospital.
- Adds a generator register as a specialist module linked to the universal asset register by a canonical asset identity.
- Adds canonical asset work-order history for faults, repairs, preventive maintenance, calibration, electrical safety tests and inspections, with status, priority, parts, costs, provider, performer and next-due fields. Asset details display this history and central admin/Biomedical users can create or update records.
- Adds trigram indexes for the asset register's case-insensitive substring search and composite indexes for hospital/status/department/category list filters and maintenance due-date/audit lookups.
- Keeps the asset register server-side paginated at 25 rows by default, with 50/100 options; filters and counts are queried from Postgres rather than downloading the full register.
- Adds individual generator profiles, basic refuelling records, service history and breakdown history.
- Adds application roles for `admin`, `biomedical` and `viewer` on the new hospital modules.
- Keeps existing `devices.ward` values as text for backward compatibility. Existing device and history rows are preserved; migration 007 adds nullable canonical `asset_id` links to faults/services while retaining legacy `device_id` values.
- Retains backward-compatible public QR lookup and reporting for legacy `EQ-…` device labels.
- Adds QR labels for canonical hospital assets. Version 3 labels encode the immutable asset UUID, current department UUID and department name; scanning opens a public fault-report page.
- Public QR pages compare both the encoded department UUID and department name with the current database record and flag stale labels after transfers.
- Ward staff do not need accounts: they scan and submit fault reports. The HOD-approved access model uses one shared Biomedical Engineering login; individual engineer attribution is therefore not available, while record history and timestamps remain available.
- Disables permanent device deletion in the interface; assets should be retired so their history remains available.
- Bumps the service-worker cache version so installed app copies can receive the new interface.

7. Apply `supabase/migrations/202611260005_department_membership_rls.sql` to staging. Test the single `biomedical` login can manage the register, confirm a no-role session cannot access internal modules, and confirm anonymous users can access only the intended QR reporting functions.

9. Apply `supabase/migrations/202611260007_link_legacy_history.sql` to staging. Verify legacy fault/service counts and canonical asset links.

15. Apply `supabase/migrations/202611280001_public_asset_qr_reporting.sql` to staging. Verify legacy QR lookup returns the current department UUID, canonical asset labels encode asset and department identity, public fault reports create one canonical work order, duplicate reports are rejected, and stale department IDs are flagged.

The repository does not contain a Supabase service-role key, and the application must never receive one. For this rollout, the HOD has approved one shared Biomedical Engineering departmental login. Assign the existing authorised Auth user the `biomedical` role. No ward logins or separate engineer accounts are to be created unless the HOD changes this decision. A shared login cannot identify which individual engineer performed an action.

Example central Biomedical role assignment (replace the UUID with the real Auth user UUID):

```sql
insert into public.app_user_roles (user_id, role)
values ('REPLACE-WITH-AUTH-USER-UUID', 'biomedical')
on conflict (user_id) do update
set role = excluded.role, updated_at = now();
```

Department memberships should be created only by admin/Biomedical after the user and department have been verified. The department membership migration is a database foundation; the app does not yet provide a staff membership administration screen.

## Initial hospital locations

The migration inserts these eight rows, using `ON CONFLICT DO NOTHING` so rerunning the seed does not duplicate names:

- Maternity Ward (ward)
- Eye Clinic (department)
- Female Ward (ward)
- Amenity Ward (ward)
- Male Ophthalmic Ward (ward)
- Operating Theatre (department)
- X-Ray / Ultrasound Unit (department)
- Accident and Emergency (department)

Locations can be deactivated instead of deleted, preserving the meaning of existing equipment records. The equipment form uses the registered active locations once the migration is available.

### Fuel and servicing safeguards

- Fuel records capture refuelling date/time, litres, amount paid, optional hour-meter reading, supplier/source and notes.
- The app does not calculate fuel consumption from a refuelling event. A defensible consumption calculation needs a measured operating-hour interval and comparable fuel-level or fuel-used data.
- Service logs accept date- and hour-based next-due information, but the app does not invent service intervals.
- Enter maintenance intervals, oil grades, coolant types, capacities and inspection criteria only after checking the correct operation/maintenance manual for the exact generator/engine configuration or obtaining written guidance from the authorised service provider.
- Load-test readings and detailed electrical performance tests are not yet represented as a structured test form in this first implementation. They should be added only after the hospital confirms its testing procedure and required measurements.

## Free-development implementation update

The canonical register interface now includes asset registration and editing for central admin/Biomedical roles, with a server-generated asset code. It also includes an atomic transfer workflow that calls migration 009; the database updates the asset's department and physical location and records transfer history in the same transaction. These controls remain unavailable until migrations 001–009 are installed and the signed-in user has an authorised role.

This update is repository-only. No Supabase migration has been applied to production, no staff role has been assigned, and no paid staging branch has been created. The transfer RPC and browser workflow still require staging-equivalent verification before production use.


## Asset maintenance and work-order history update

The repository now contains migration `202611270001_asset_work_order_history.sql` and a canonical asset details/history screen. Work orders are linked to the canonical asset and hospital, rather than being stored as unlinked notes. Supported types are fault, repair, preventive maintenance, calibration, electrical safety test, inspection and other. Records include priority, status, report/performance date, scheduled date, description, action taken, parts, performer, external provider, cost and next-due date/hour-meter reading.

For now, creation and updates are restricted to the central `admin` and `biomedical` roles. This is deliberate: department-officer and maintenance-role write permissions remain unconfigured until the HOD discussion. View access follows the existing department-scoped canonical asset policy. The new migration is additive and does not rewrite or delete the legacy `faults` or `services` tables. Their history-linking migration remains a separate rollout step.

This is a repository change only. The new migration has not been applied to the live Supabase database, and the new screens will not become operational until the complete migration sequence is safely tested and approved for rollout.


## Capacity and reliability update

Migration `202611270002_capacity_search_indexes.sql` enables the `pg_trgm` extension in the `extensions` schema and adds trigram indexes for name, asset code, model and serial number. These align with the current application's `ILIKE '%term%'` search. Composite indexes support common hospital/status/department/category list filters, while additional indexes support maintenance due-date and audit-history lookups. The existing full-text search index and unique asset-code constraint remain in place.

The asset register already performs database-side filtering and server-side pagination. It requests only the selected page, defaults to 25 rows, and offers 50/100 rows per page. This work strengthens database indexing rather than downloading thousands of assets to the browser.

Two staging-only test assets are included:
- `supabase/tests/capacity_10000_assets.sql`: creates 10,000 synthetic assets, captures query plans/timings for a paginated list, a department/status filter and substring search, verifies the count, then rolls the transaction back.
- `tests/load/asset-register.k6.js`: optional 50-virtual-user, two-minute read-load test. It requires a dedicated staging URL, publishable/anon key and staging-user access token. It must never be pointed at production or supplied a service-role key.

These are test harnesses, not proof that 10,000 assets or 50 concurrent users have already been load-tested. The current Supabase project has no hospital foundation tables installed, and no paid staging branch was created. Run the test scripts only after an isolated staging database is available and the migration sequence has been installed there.
